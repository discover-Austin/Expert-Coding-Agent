# Day 5 Complete: Error Recovery & Learning

**Goal:** When things break, learn WHY and HOW to prevent it.

**Deliverable:** Agent learns from every error, applies to future work.

## What Was Built

### ErrorAnalyzer (`src/error_analyzer.py`)

Deep failure analysis engine that turns raw test failures into structured diagnoses with recovery strategies.

**Core capabilities:**

1. **Stack trace parsing** — Extracts structured `StackFrame` objects (file, line, function, code) from Python tracebacks.

2. **Error classification** — Maps 15+ Python exception types to `ErrorCategory` enums with violated assumptions and default fix suggestions. Falls back to heuristic classification for unknown error types.

3. **Recovery strategies** — Generates ordered `RecoveryStrategy` objects based on error category, severity, and available options (rollback, fix-and-retry, retry, skip, escalate). Each strategy has confidence, preconditions, and executable steps.

4. **Learning loop** — Every analyzed failure feeds into `FailureTaxonomy` (for archetype formation) and `KnowledgeCore` (for empirical confidence tracking). Recovery outcomes are also recorded.

5. **Failure clustering** — `build_failure_taxonomy()` groups failures by root cause category, giving a structured view of where the system is breaking.

6. **Trend analysis** — `analyze_failure_trends()` tracks most common error categories, severity distribution, and frequently violated assumptions across all recorded failures.

### Integration into ProductionCodingAgent

- New `analyze_and_recover()` method: full pipeline from test failure to recovery execution.
- Enhanced `_learn_from_failure()`: uses ErrorAnalyzer for deep analysis instead of raw string recording.

## Architecture

```
TestResult (from CodebaseExecutionEngine)
    ↓
ErrorAnalyzer.analyze_test_failure()
    ↓
FailureAnalysis (per test failure)
    ├── Stack trace parsing → StackFrame[]
    ├── Error classification → ErrorCategory + violated assumption
    ├── Severity assessment → FailureSeverity
    ├── Similar past failures → FailureTaxonomy.rank_archetypes()
    └── Suggested fixes → taxonomy-informed + rule-based
    ↓
RecoveryStrategy[] (ordered by confidence)
    ↓
execute_recovery() → RecoveryResult
    ↓
learn_from_failure() + learn_from_recovery()
    ├── FailureTaxonomy (archetype formation)
    └── KnowledgeCore (empirical confidence)
```

## Key Design Decisions

### Why classify errors, not just parse them?
Classification maps symptoms to root causes. "AttributeError" is a symptom; "code assumed an object had an attribute it doesn't" is the violated assumption. The assumption is what we learn from.

### Why recovery strategies, not just rollback?
Different failures need different responses. Import errors can be fixed by installing a dependency. Timeouts can be retried. Concurrency errors need investigation. Rollback is always available but not always the best first step.

### Why learn from recovery outcomes?
A recovery strategy that works becomes more confident for similar future failures. One that fails gets penalized. This is the compounding loop — session 100 knows which recoveries actually work.
